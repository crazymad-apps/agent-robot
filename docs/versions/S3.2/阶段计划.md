# S3.2 阶段计划

## 1. 实施原则

- 先基于实际代码和测试完成整体架构 Review，再决定是否需要调整实现。
- Review 不以“重构”为默认结论；没有明确风险、故障证据或职责冲突的实现可以保持。
- 连接状态、媒体状态和 Runtime 业务状态必须各有单一权威来源，不能用 UI 状态反推业务事实。
- 输入分段、TTS 分段和网络帧分别使用明确 ID、所有权转移和有界队列，不靠时间巧合维持正确性。
- device protocol 1.0 继续冻结；跨仓 wire 变化必须先走联合变更门。
- 不引入 S3.3/S3.4 的 UI 控件或 WakeNet 变量，避免媒体问题与新交互并行进入主链。
- 不覆盖两仓现有用户改动；所有写操作前重新核对目标文件和工作区状态。

## 2. P0：冻结 Review 输入

### 工作

1. 记录 agent-robot 与 ez-assistant 的精确提交、dirty 文件、构建工具、配置和协议快照。
2. 盘点两仓正式实现入口、组件依赖、任务/线程、队列、状态所有者和现有测试。
3. 从 S3.1 验收记录提取已通过证据、延期矩阵和已观察故障，不把历史计划当成当前实现事实。
4. 跑只读或非破坏性的现有测试基线；不能运行时记录环境缺口，不推定通过。

### 阶段门

- Review 使用的代码、文档、fixtures 和测试结果均可定位到精确版本。
- 两仓用户未提交改动已识别且未被覆盖。
- 已形成从设备 PTT 到 Runtime 提交、以及从 `speak` 到设备播放的实际调用链清单。

## 3. P1：整体架构 Review 门

### 工作

按 [`架构Review.md`](架构Review.md) 逐项检查：

1. 系统拓扑和组件职责。
2. 连接、身份、输入、Runtime Run、输出和 UI 投影的权威状态。
3. FreeRTOS 任务、Host async task、锁、队列、缓存和背压。
4. 连续输入、ASR、Runtime 提交、TTS FIFO、取消及迟到事件的时序。
5. 网络、Host、Provider 和设备重启恢复。
6. WSS、设备身份、Provider 凭据、日志和隐私边界。
7. 内存、PSRAM、栈、缓冲上限、超时及可观察性。
8. device protocol、assistant-protocol 和跨仓版本职责。
9. 当前 GPIO、音频、显示、功放、供电和 ESP32 资源假设与正式固件的硬件/软件边界。

### 产出

- 每个 Review 项均有实现证据和“保持 / 调整 / 延后”结论。
- 每个调整项记录严重度、根因、目标组件、所属仓库、协议影响、验证方法和目标版本。
- 需要改变当前路线、协议或跨仓职责时，先提交方案给用户确认，不自行扩大实施范围。

### 阶段门

- 不存在责任归属不明的阻断或高优先级问题。
- 所有高优先级问题已进入 S3.2 实施清单；延后项有不影响当前基线的证据。
- 若协议保持不变，明确记录“无需解冻”；若必须修改，联合变更方案已经确认后才进入 P2。

## 4. P2：输入与 Provider 收敛

> 当前进度：P2-M1（S32-R01～R03）与 P2-M2（S32-R04）已完成；2026-09-05 用户要求推进版本主线，
> 进入 P2-M3（S32-R05）。Provider 收敛已完成代码实现和自动化验证。用户进一步授权直接推进到人工
> 验证阶段，本次连续完成 P3 与 P4 的可自动执行工作，每一步仍单独验证并记录，不再逐里程碑等待确认。

2026-09-05 按用户“继续开发”推进播报中断专项：修复 S32-R09 的迟到结束消息导致队首永久等待，
补齐终端播放原因与进度诊断。此项属于已报告故障的优先处置，不表示 P2/P3 整阶段通过；Provider
收敛和 Host 队列接纳确认仍保留在原计划。真实语音复验需要 Host 开启设备接入。

### 工作

1. 固化 Provider 配置装配、启动、健康状态、超时、取消、错误映射、退避和恢复行为。
2. 验证 PTT down 事件在 Host 及时介入连续输入窗口；Runtime 提交前的新分段保留并合并上一分段。
3. 覆盖空录音、无有效 transcript、迟到/重复 ASR 结果、ASR 超时、断线重传和分段确认丢失。
4. 保证同一逻辑输入只提交一次，不同逻辑输入不会因错误去重而丢失。

### 实施里程碑

| 里程碑 | 范围 | 状态 |
|---|---|---|
| P2-M1 输入可靠性 | S32-R01：PTT 边沿可靠交付；S32-R02：取消未接管分段后恢复聚合收口；S32-R03：异常 stop 与旧 Run 取消失败一致收口 | 已完成 |
| P2-M2 识别任务所有权 | S32-R04：识别任务的完成、panic、取消和 shutdown 均产生可回收终态 | 已完成 |
| P2-M3 Provider 收敛 | S32-R05：ASR/TTS 独立健康状态、恢复和并发/内存预算 | 已完成 |

### 阶段门

- Provider 不可用或恢复时，Host 主链保持可降级且终端可回到可操作状态。
- 连续分段、空输入和重传自动化通过，Runtime 提交次数与预期精确一致。
- Provider credential、完整语音和 transcript 不进入普通日志。

## 5. P3：TTS 队列与终端播放收敛

> 2026-09-05：开发和自动化完成。新增内部接纳回执及取消 guard，不改 wire；设备相关 Rust
> 回归 28 项通过。真实多段实听仍纳入 P4，不以自动化代替物理播放验收。

### 工作

1. 明确 TTS 分段的排队、合成、下发、队列接纳、发送完成、终端消费、取消和丢弃状态；不把
   `speak` Tool 成功误写成扬声器物理播放完成。
2. 验证首段预缓冲、后续 FIFO、多段长回复、慢设备背压和队列上限。
3. 验证 PTT 抢占、旧 stream 迟到 PCM、连接 epoch 变化和下一轮播放隔离。
4. 检查终端统一下行 FIFO 的内存所有权、释放路径、underrun 恢复和播放增益边界。

### 阶段门

- 多段回复不漏播、不乱序、不重复；任一段失败不会让后续轮次永久堵塞。
- PTT 可立即停止当前及剩余播报，旧音频不能混入新一轮。
- 终端播放 FIFO 和 Host TTS FIFO 都有有界容量、明确满载策略和诊断计数。
- S3.2 不新增物理播放完成 wire ack；如果后续产品语义确实依赖该事实，再走联合协议变更门。

### S3.2 完成门

- 至少 20 轮真实 PTT 对话无漏播、重复提交、不可恢复状态、崩溃或持续内存下降。
- Provider、连续输入和 TTS 队列的关键错误都能恢复到 `idle` 或 `disconnected`。
- 两仓相关自动化、固件 release 构建和必要 ESP32 实机验证通过。
- 组合版本、指标、偏差、延期项和用户实听结论已写入 [`验收记录.md`](验收记录.md)。

## 8. 停止条件

出现任一情况立即停止对应实现并记录：

- Review 发现权威状态重复、无界队列、无法证明所有权的媒体内存或跨轮迟到数据污染。
- 需要修改协议、Runtime 业务语义或跨仓职责，但尚未取得明确确认。
- 自动化影响计数与预期不符，或失败后只能靠重启整机恢复。
- internal heap、PSRAM、最大连续块或关键任务栈出现无法解释的持续恶化。
- 修复需要兼容旧 Demo、加入生产测试分支、弱化 WSS/身份校验或记录敏感数据。
- 工作区出现与本阶段无关且会被覆盖的用户改动。
