资源与恢复口径：

- ASR 单句最多 1,920,000 byte（60 秒 PCM16/16 kHz/mono），4 个已接纳请求合计原始输入最多
  7,680,000 byte；TTS 单次最多 120 字，2 个进行中的输出 PCM 合计最多 3,840,000 byte。
- 以上是语音服务请求载荷预算，不是进程 RSS 上限。WAV/Base64/JSON 转换、网络缓冲、Gateway
  已交付的每连接 20 段播放队列以及终端 FIFO 需分别计入 P3/P4 的资源观察，不能由本项代替。
- 默认 30 秒、最大 120 秒的超时覆盖整次调用，TTS 合成和 PCM 下载不再各自消耗完整总时限；
  shutdown/请求取消覆盖 debug I/O。没有新增自动重试、后台收费探测或失败音频重放，也没有隐式
  退避等待；恢复由下一次显式请求验证，成功后更新为 ready。
- 配置缺失/无效须修正后 reload；服务 actor 退出仍遵循既有 HostSupervisor 的降级策略，不在本项
  增加自动重启。已有 PCM 协商能力的连接可直接重试；若建立连接时没有协商 PCM，需要重新连接。

### 4.1 2026-09-05 播报中断专项（S32-R09）

9 月 2 日用户反馈第二段 `speak` 播到一半停止。当时查询到最新 Run 正常完成、4 个 `speak`
均返回 `accepted: true`，没有记录 Run 取消。该结果仅证明 Host 队列接纳，不证明终端播完；
当时缺少与故障时刻对应的播放结束原因及消费进度，不能认定发送超时，也不能凭事后资源快照
彻底排除故障时刻内存不足。9 月 5 日旧串口会话已失效，未恢复出该次故障日志。

此次通过源码和正式 worker 自动化确定另一个可复现的播放阻塞路径：最后 PCM 已消费，
`playback_end` 尚未到达，I2S 缓冲耗尽后进入 rebuffer；随后结束消息到达，队首已 drained，
但原任务先等待 head ready（空队首永远不能再次 ready），导致后续流也无法推进。

修复及验证：

- `audio_io_task` 在等待预缓冲前先处理 drained；仍有 I2S 缓冲时等待排空，已停止的 I2S
  不再次调用 stop，也不重新启动空流，完成后推进下一项。
- `audio_io_playback_test.c` 通过测试目录内的 FreeRTOS/I2S 适配驱动正式 `audio_io.c`，
  覆盖正常两段、迟到 end、重缓冲期间取消以及后续轮次。测试使用确定性时钟，不调用真实 Provider。
- 对 `0384f64` 的原 `audio_io.c` 运行同一测试，退出 134，命中第二次空队首等待断言；
  当前实现全量 `firmware/test/run_host_tests.sh` 通过。
- 本机默认 Xcode 因许可证未接受而无法启动编译器；使用已安装的
  `DEVELOPER_DIR=/Library/Developer/CommandLineTools` 运行 Host tests，通过；未更改系统配置。
- 新增 `playback_end_received`（stream/epoch/已知 reason/result）、`audio_ingress_rejected`、
  `playback_rebuffer`，并在播放事件携带 received frames、consumed samples、sample count 和
  queued frames。无逐帧普通日志、不记录音频/正文/凭据；消费计数是软件队列进度，不是硬件完成 ACK。
- `firmware/idf.sh build`、生产命名检查、第三方源校验通过。镜像 `0x140a30`（1,313,328 bytes），
  app partition 剩余 `0x1bf5d0`（58%）。SHA-256：
  `754985aec26fd7a6791ab0ed5dbe4b50ba9095cd84100e8ac0b8ab12cc7ce75f`。

- 同次只读查询 Host：`enabled=false`、`available=false`，ASR/TTS 为 ready，终端身份仍 paired。
