# Agent 硬件终端实施路线

> **文档状态：当前执行主线。**
>
> 本文档负责定义项目的实施顺序、阶段范围和验收条件。硬件和软件的职责、接口与约束分别以
> [`hardware-architecture.md`](hardware-architecture.md) 和
> [`software-architecture.md`](software-architecture.md) 为架构基线；仍标记为冻结点的事项，
> 必须在本文档对应阶段完成验证或联合设计后确定。

阶段一硬件原型、S2.0–S2.3 以及 S3.0 Demo 链路验证已完成；S3.1 已进入正式协议实施。
S3.0 已用隔离的简易 Voice Demo Host 验证设备通信、ASR、Agent SDK、TTS、连续 20 轮 PTT
和主要故障恢复；这些证据只作为正式接入输入，Demo Host 已冻结归档，不进入产品架构。S3.1
以 ez-assistant v0.21.0 联调工作树为暂时冻结基线：Device Gateway 与 SpeechService 作为
Runtime Host 的可降级子系统，终端通过 LAN WSS `/device` 接入；Desktop 继续使用原有
loopback HTTP/SSE。联调中若发现协议缺口，可以在 ez-assistant 同步修改并重新冻结 fixtures。

## 1. 路线目标

用分阶段方式完成一个以 ESP32-S3 为核心的桌面 Agent 语音终端：

1. 先通过分体模块完成硬件组装和各功能点验证，建立稳定的飞线原型。
2. 在飞线整机上验证 2.4 GHz Wi-Fi、断线恢复和本地离线唤醒，确认持续收音与联网可以共存。
3. 再接入本地 ez-assistant，使终端具备完整的语音对话链路。
4. 在软硬件接口稳定后设计并打样 PCB，同时让外壳支线逐步收敛，最终完成整机装配。

项目坚持“先验证、后集成”：前一阶段未通过验收，不把未经验证的假设固化到 PCB 或外壳中。

## 2. 总体阶段

| 阶段 | 核心结果 | 主要形态 |
|---|---|---|
| 阶段一：硬件原型 | 屏幕、收音、放音、按键可分别验证，并能组成稳定飞线整机 | DevKitC-1 + 分体模块 + USB 供电 |
| 阶段二：联网与本地唤醒 | 验证 Wi-Fi 连接/重连、WakeNet 离线唤醒和全外设资源共存 | 飞线整机 + 本地 Wi-Fi |
| 阶段三：Agent 接入 | 先以隔离 Demo 验证通信、ASR/TTS 和 Agent 链路，再与 ez-assistant 联合确定正式接入 | 飞线整机 + PC 本地服务 |
| 阶段四：PCB 与整机 | 飞线方案固化为自绘 PCB，完成板级验证和外壳装配 | 自绘 PCB + 3D 打印外壳 |

外壳设计作为贯穿式旁支推进，但不能先于关键机械约束定型，详见 §7。

## 3. 阶段一：硬件组装与功能点验证

### 3.1 阶段目标

不依赖 ez-assistant 和真实语音服务，独立跑通终端硬件的输入、输出、显示和基础交互，
形成可供阶段二继续开发的稳定飞线原型。

### 3.2 实施顺序

#### S1.0 准备与约束确认

- 阶段入口：[`versions/S1.0/`](versions/S1.0/)
- 确认 DevKitC-1、屏幕和各模块的准确版本、供电要求及实际引脚定义。
- 冻结飞线阶段 GPIO 表，避开启动配置、板载器件和 Flash/PSRAM 占用引脚。
- 建立 ESP-IDF 工程和可复现的编译、烧录、串口日志流程。
- USB 供电起步；电池、电源路径和低功耗不进入本阶段。

#### S1.1 放音验证

- 接入 I2S 功放和喇叭，先播放低幅度间歇测试音，再播放已知 PCM 样本。
- 验证静音、音量调整、功放使能和连续播放。
- 记录不同供电和音量下的噪声、失真及供电稳定性。

#### S1.2 显示验证

- 点亮 ST7789，完成颜色、方向、背光和刷新验证。
- 接入 LVGL，显示最小状态页。
- 验证 SPI 与 DMA 工作稳定，不出现持续花屏或刷新阻塞。

#### S1.3 收音验证

- 接入单个 I2S 麦克风，采集固定格式 PCM。
- 输出音量或波形诊断，并将样本导出为可在 PC 播放的音频文件。
- 检查底噪、削波、左右声道选择和采样位宽转换。

#### S1.4 飞线整机联调

- 同时接入屏幕、麦克风、功放、喇叭和按键。
- 实现 `idle / listening / playing / error` 本地状态机。
- 用按键控制录音和播放，完成本地录音回放闭环。
- 固化接线图、GPIO 表、音频格式和已知问题。

### 3.3 本阶段暂不做

- Agent、语音接入层、ASR、TTS 和 WSS。
- 唤醒词、双麦、回声消除和波束成形。
- 电池供电、充电管理和低功耗。
- 自绘 PCB 和正式外壳。

### 3.4 交付物

- 可重复搭建的飞线接线图和准确 GPIO 表。
- 能独立演示点屏、收音、放音、按键和录音回放的固件。
- 音频样本、测试记录、供电记录及问题清单。
- 阶段二可依赖的音频输入输出接口和本地状态机。

### 3.5 阶段门

满足以下条件后才能进入阶段二：

- 所有必选硬件可以同时连接，不存在引脚或供电冲突。
- 录音样本可辨识且无持续削波，播放无明显持续中断。
- 本地录音回放和按键交互可重复运行。
- 连续运行至少 30 分钟，无重启、死锁或明显资源泄漏。
- 接线、配置和复现步骤已经记录，而不是仅在当前样机上偶然可用。

## 4. 阶段二：联网与本地唤醒验证

### 4.1 阶段目标

保持阶段一接线不变，不依赖 ez-assistant、ASR、TTS 或设备 WSS 协议，独立验证：

```text
2.4 GHz Wi-Fi 连接/重连 ─┐
                         ├─ 与屏幕、PTT、持续 I2S 收音共同稳定运行
INMP441 → AFE/WakeNet ───┘
              │ 唤醒命中
              └─▶ 本地提示与一次录音回放闭环
```

本阶段回答“当前 N8R8 飞线整机能否可靠联网并持续离线监听”。内置 WakeNet 模型只负责产生
本地唤醒事件，不提交 Agent 请求；PTT 始终保留为回退入口。

### 4.2 实施顺序

#### S2.0 联网与唤醒约束确认

- 阶段入口：[`versions/S2.0/`](versions/S2.0/)
- 核对 ESP-SR/WakeNet 与当前 ESP-IDF、ESP32-S3 N8R8、16 kHz 单声道 PCM 的兼容组合。
- 选择首个官方内置唤醒模型，冻结模型分区、应用分区和录音缓冲的 8 MB Flash 布局。
- 定义 Wi-Fi 凭据注入与 NVS 保存方式；SSID、密码和密钥不得提交仓库或写入普通日志。
- 建立阶段测试矩阵、资源基线和明确的停止条件，不先接入 ez-assistant。

#### S2.1 Wi-Fi 连接与恢复

- 以 Station 模式连接 2.4 GHz AP，通过 DHCP 获取地址并显示连接状态。
- 输出受控诊断：连接状态、RSSI、IP、重连次数和最近错误；不输出密码。
- 验证 AP 断开、路由器重启、错误密码、信号变弱和开发板重启后的恢复行为。
- 保持 PTT 本地录音回放可用，网络任务不得阻塞 I2S 或 LVGL。

#### S2.2 WakeNet 离线唤醒

- 将 INMP441 的 16 kHz、单声道、PCM16 连续音频送入 ESP-SR AFE/WakeNet。
- 首先使用官方内置唤醒词验证算法链路；自定义唤醒词不作为本阶段前置条件。
- 记录唤醒命中、误触发、阈值、检测延迟和测试距离，保留 PTT 手动触发。
- 唤醒后只执行本地状态提示和一次录音回放，不连接 ASR、TTS 或 Runtime。

#### S2.3 联网、唤醒与媒体共存

- 同时运行 Wi-Fi、WakeNet、I2S RX、ST7789/LVGL、PTT 和本地音频播放。
- 首版继续半双工：播放时暂停 WakeNet，播放结束后恢复监听，不实现播放中语音打断。
- 仅记录应用尺寸、内部堆/PSRAM 快照、Wi-Fi 重连、唤醒和明确错误，不在原型功能阶段引入重型性能监控。
- 各执行一次正常联网、AP 断开/重连中、AP 恢复后的 WakeNet 与 PTT 本地闭环，确认无黑屏、重启或不可恢复状态。

> 阶段二只验证功能节点和最小共存可行性，不代替严格可靠性验收。原 S2.4 的
> 60 分钟长稳、资源趋势、极端网络/供电与统计性唤醒测试延期到 S4.0 PCB 输入冻结前执行。

### 4.3 本阶段暂不做

- ez-assistant 联合版本、Runtime、ASR、TTS、WSS 和设备配对协议。
- 自定义唤醒词量产模型、云端唤醒、离线命令词系统。
- 播放期间唤醒、AEC、双麦、波束成形和免唤醒打断。
- 5 GHz Wi-Fi、BLE 配网、OTA、电池和低功耗待机。

### 4.4 交付物

- 可复现的 Wi-Fi 配置、连接、诊断和退避重连实现。
- ESP-SR/WakeNet 模型与分区配置、输入适配和本地唤醒演示。
- 联网、持续收音、屏幕、PTT 和播放共存的固件与基础资源快照。
- 唤醒功能、Wi-Fi 故障恢复和最小共存冒烟记录。

### 4.5 阶段门

满足以下条件后才能进入阶段三：

- 能连接指定 2.4 GHz AP，并在 AP 恢复后自动重连；凭据不进入仓库和普通日志。
- 在约 0.5～1 米安静环境可重复唤醒，并记录实际模型、阈值与已知漏检；不把原型结果外推为量产指标。
- 唤醒、PTT、本地录音回放和屏幕状态可重复运行，Wi-Fi 故障不会阻塞音频关键路径。
- Flash 分区已核验，并保留内部堆与 PSRAM 快照；长时趋势、关键任务栈和极限余量留待 S4.0 PCB 输入冻结前验证。

## 5. 阶段三：Agent 接入

### 5.1 阶段目标

保持阶段一硬件不变，通过与 ez-assistant 同步规划的语音接入层接入 Runtime，完成：

```text
按键开始说话 → 终端采集 → 语音接入层 ASR → Runtime
              终端播放 ← 语音接入层 TTS ← Runtime 回复
```

阶段三的 S3.1 只保留按键 PTT 作为 ASR 触发入口，不编译或运行 WakeNet；阶段二通过的本地唤醒
证据保留给正式设备链路稳定后的独立版本，不得让唤醒模型问题进入首次 Agent 主链诊断。音频压缩
同样属于后续增强。

这里的“语音接入层”是职责名称。当前物理形态已经确定为 ez-assistant Runtime Host 内的
Device Gateway 与 SpeechService 模块；它们与 Desktop HTTP/SSE 共用一个 Host 进程，但与
Runtime 权威业务状态保持清晰边界。

### 5.2 Demo 验证与联合版本规划

为避免 ez-assistant 主体版本阻塞硬件链路验证，阶段三先允许在 agent-robot 中实现隔离的
Voice Demo Host。它可以用本地路径直接引用 ez-assistant 的 `agent-sdk`，只验证设备通信、
ASR、Agent 单次执行和 TTS 播放，不提供正式 Runtime Host 语义。

Demo Host 的代码、消息格式、无鉴权连接、内存态上下文和进程生命周期均为阶段验证实现：

- 不进入 `assistant-protocol`，不承诺向正式版本兼容。
- 不持有或模拟正式 Session、Run、Conversation、审批、队列和恢复事实。
- 不把局域网无鉴权连接表述为正式安全方案。
- 不修改或扩展 ez-assistant 当前 Runtime Host 的 loopback-only 边界。

Demo 链路通过后，ez-assistant v0.21.0 联调工作树已经给出正式 Device Gateway、SpeechService、
device protocol v1.0 和 Node/H5 虚拟终端。S3.1 直接以这些实现和跨语言 fixtures 为基线联调。

联合设计至少需要回答：

1. ESP32 与 Rust/Node fixtures 的 JSON envelope、PCM 帧头和加密 transcript 是否逐字节一致。
2. mDNS、WSS 证书指纹、SPAKE2 配对与 Ed25519 认证能否在真实局域网和断线恢复下稳定工作。
3. PTT 上行、DashScope ASR、当前 Controller Session、`speak` TTS 队列与播放取消能否完整闭环。
4. Host、Gateway、SpeechService 或 Provider 故障时，终端状态与 Host 可降级语义是否一致。
5. 两个项目的提交、协议版本、能力位、fixtures 和兼容窗口如何组成可复现组合版本。

#### 职责基线

以下边界可以作为联合设计的起点，但不提前决定进程拓扑：

| 职责 | 权威归属 |
|---|---|
| Session、Run、Conversation、队列、审批、权限、幂等和事件序号 | ez-assistant Runtime |
| Runtime 本地启动、实例发现、Desktop loopback HTTP/SSE、Device Gateway 和 capabilities | ez-assistant Runtime Host |
| 局域网设备配对、设备身份、WSS、音频流、ASR/TTS 和终端状态映射 | ez-assistant Device Gateway / SpeechService |
| 采集、播放、屏幕、按键、设备本地状态和断网提示 | agent-robot 终端 |

无论最终采用哪种拓扑，都必须遵守：

- 语音接入层不持有第二份 Session、Run 或 Conversation 权威状态。
- 不复制一套与 Runtime Host 并行的业务命令、持久化和恢复协议。
- assistant-protocol 继续表达 Agent 业务语义；设备音频与控制协议保持为独立的窄媒体协议。
- Device Gateway 与 SpeechService 虽在 Host 进程内，媒体、设备和 ASR/TTS 依赖仍不能渗入
  Runtime 业务状态或 assistant-protocol 的核心 DTO。

#### 正式版本同步门

进入正式 Runtime 接入前应形成一组配套版本输入：

- ez-assistant：当前以 v0.21.0 联调工作树和 device protocol v1.0 为基线，发布前补充可复现提交。
- agent-robot：实现并记录支持 device protocol v1.0 的终端固件版本。
- 联合验收：确定端到端组合版本和兼容矩阵。

协议联调期间允许必要修改，但每次修改都要同步 schema/fixtures、两端实现和组合验收记录；
ez-assistant v0.21.0 正式发布后再用发布提交替换联调工作树描述。

### 5.3 实施顺序

#### S3.0 Demo 链路验证

- 在 `agent-robot` 中建立 Rust Voice Demo Host，以本地路径引用 ez-assistant `agent-sdk`。
- `demo.1` 先用无鉴权 WebSocket 完成 PCM 上送、原样回传和状态控制，不接 ASR 或 Agent。
- `demo.2` 完成整句话 ASR、固定或回显文本 TTS 和终端播放。
- `demo.3` 把 ASR 文本提交给 `agent-sdk` 临时执行入口，再将回复交给 TTS。
- 首版只支持单设备、PTT 半双工和内存临时状态；PTT 松开定义话语结束。
- 记录延迟、缓冲、错误和资源证据，形成正式联合设计输入，不冻结 Demo 私有协议。

#### S3.1 终端与语音接入层通信

- 阶段入口：[`versions/S3.1/`](versions/S3.1/)
- 基于 ez-assistant device protocol v1.0 fixtures 从零实现终端 codec，不兼容 S3.0 私有协议。
- 接入 mDNS `_ez-assistant._tcp.local`、WSS `/device`、证书指纹、6 位码 SPAKE2 配对和
  Ed25519 设备认证；不使用预共享 token。
- 先设 codec/密码学与 TLS pin/WSS 两个可行性门，再完成配对、认证、PCM 和状态控制。
- 不增加测试专用 wire；自动化媒体测试复用正式 fixtures/M7，实机首次闭环直接接入现有正式 Host、
  当前 Controller Session 和真实 ASR/TTS，至少连续完成 5 轮 PTT。
- 验证断线重传、连接替换、乱序/非法帧、超时、设备撤销和播放取消。

#### S3.2 ASR/TTS 接入

- 将一段完整话语转换为文本，并把文本转换为可流式播放的音频。
- 明确语音结束检测方式；首版可以由 PTT 松开结束录音。
- 定义 TTS 分句、缓冲、打断和错误恢复策略。

#### S3.3 Runtime 接入

- 在 ez-assistant 中完成对应版本设计，确认语音接入层的归属、进程形态、生命周期和正式安全边界。
- 记录 ez-assistant 依赖版本、assistant-protocol 版本和所需 capabilities。
- 语音接入层按联合设计复用 ez-assistant 的正式客户端或 Host 能力，不另造 Runtime 业务协议。
- 创建或恢复终端使用的 Session，提交 ASR 文本并消费实时事件。
- 将 Runtime 状态映射为终端可显示的 `idle / listening / thinking / speaking / needs_attention / error`。
- 处理 Run 取消、审批等待、Runtime 重启和事件水位重新对齐。

#### S3.4 端到端收敛

- 完成多轮语音对话、文本上屏和回复播放。
- 验证说话结束到首段回复播放的延迟，并定位 ASR、Runtime、TTS 各段耗时。
- 验证断网重连不会重复提交用户输入或重复朗读历史回复。
- 记录语音接入层与当前 assistant-protocol 版本的对应关系。

### 5.4 本阶段暂不做

- 在终端上管理 Workspace、记忆、模型配置和历史会话。
- 在终端上审批工具操作。
- 公网部署、多用户和远程 Runtime。
- 以 Opus、双麦、播放中唤醒或自定义唤醒词作为首版前置条件。

### 5.5 交付物

- 两项目共同确认的组件职责、进程拓扑、版本依赖和兼容矩阵。
- 语音接入层及其配置、启动和诊断说明。
- 终端 WSS 客户端、音频缓冲、状态机和错误展示。
- 固化的 device protocol 组合版本、fixtures 来源与兼容策略。
- 可重复执行的端到端验收记录。

### 5.6 阶段门

满足以下条件后才能把方案固化到 PCB：

- 可以连续完成至少 20 轮 PTT 语音对话。
- 终端、语音接入层或 Runtime 任一方重启后可以恢复到可用状态。
- 播放可被明确打断，取消行为不会误伤后续一轮对话。
- 断线重试不会造成同一句输入重复提交。
- 审批、网络错误、ASR/TTS 错误均有可识别状态，不会无限停留在 `thinking`。
- 阶段一的 GPIO、音频格式、缓冲规模和供电要求已经稳定。
- 阶段二冻结的 Wi-Fi、WakeNet、分区和资源基线没有被接入实现破坏。

## 6. 阶段四：PCB 设计、打样与整机集成

### 6.1 阶段目标

把已经通过端到端验证的飞线方案转化为可装配的自绘 PCB；完成首板焊接、板级验证，
并与外壳支线汇合形成整机。

### 6.2 实施顺序

#### S4.0 PCB 输入冻结

- 在最终飞线原型上执行严格可靠性验收：长时运行、资源趋势、重复唤醒、网络/供电故障和峰值功耗；未通过前不冻结 PCB 输入。
- 冻结主控模组、屏幕接口、麦克风、功放、喇叭、按键和调试接口。
- 重新核对器件生命周期与可采购性；飞线模块型号不自动等于 PCB 最终器件。
- 冻结 PCB 外形、安装孔、屏幕窗口、麦克风孔、出声方向、USB 和按键位置。
- 首板不加入电池；冻结 USB 5V、功放支路和 3.3V 逻辑电源树。

#### S4.1 原理图与 PCB

- 绘制原理图，完成电源、启动、下载、复位、去耦和保护设计。
- 进行布局布线，优先处理天线净空、电源完整性、音频干扰和机械边界。
- 在下单前完成原理图、封装、BOM、网络表和制造文件复核。

#### S4.2 打样、焊接与板级 Bring-up

- 首板分电源、主控、屏幕、收音、放音、网络的顺序上电验证。
- 任一步骤异常时停在当前层排查，不直接进行整机联调。
- 复用阶段一至三的测试程序和验收用例，对比飞线原型与 PCB 的表现。

#### S4.3 外壳装配与整机验收

- 使用已冻结的 PCB 和器件三维尺寸完成外壳定型和试打印。
- 验证屏幕视角、按键手感、USB 可达性、麦克风拾音、喇叭音腔、散热和装配公差。
- 完成整机长时间运行、网络恢复、语音链路和重复拆装验证。
- 记录首板问题，决定小改手工修正还是进入 PCB v0.2。

### 6.3 交付物

- 原理图、PCB、BOM、Gerber、贴片/焊接资料和板级测试记录。
- 可运行阶段三完整软件链路的 PCB 样机。
- 外壳源文件、打印文件、装配说明和整机照片。
- PCB v0.1 问题清单及是否需要 v0.2 的结论。

### 6.4 阶段完成标准

- PCB 能替代飞线原型完成全部核心功能。
- 整机连续运行、重连和多轮语音对话达到阶段二、三基线。
- 没有影响启动、烧录或正常使用的结构干涉。
- 麦克风和喇叭安装后仍达到可接受的拾音与播放效果。
- 设计文件和装配步骤足以再次制作一台相同设备。

## 7. 外壳设计旁支

外壳不必等到阶段四才开始，但应分层推进：

| 时点 | 可以开展 | 不应提前冻结 |
|---|---|---|
| 阶段一 | 外观方向、桌面摆放方式、屏幕角度、按键位置、喇叭与麦克风相对方向 | 精确开孔、固定柱、PCB 外形 |
| 阶段二 | 纸模/泡沫模型、Wi-Fi 天线净空和持续监听声学实验 | 最终内部结构和装配公差 |
| 阶段三 | 交互体验、线缆出口和语音链路声学隔离实验 | 最终内部结构和装配公差 |
| 阶段四 S4.0 后 | PCB 外形、安装孔、器件高度和接口位置均已冻结，可完成正式 CAD | — |

外壳支线持续产出约束和样机，但正式打印件必须以冻结后的 PCB 与实物测量为准。

## 8. 延后路线

以下能力不进入四阶段核心完成标准，待基础整机稳定后单独评估：

- 自定义唤醒词量产模型和播放中语音唤醒。
- 双麦、AEC、降噪和波束成形。
- 电池供电、充电底座和低功耗待机。
- Opus 音频压缩。
- 灯环、触摸和更多显示动画。
- 移动底盘、摄像头及其他执行机构。

## 9. 文档使用规则

- 本文档回答“按什么顺序做、何时进入下一阶段”。
- `hardware-architecture.md` 定义硬件边界、总线、GPIO、电源、PCB 迁移和机械接口。
- `software-architecture.md` 定义 Runtime、语音接入层、终端固件和设备协议边界。
- 实施中形成的新结论先写入当前阶段记录；通过阶段验收后，再同步更新对应架构基线。
