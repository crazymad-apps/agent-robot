# S3.2 人工验收

状态：自动开发与回归已完成，**尚未通过实机验收、封版或提交**。候选版本和自动化证据见
[`验收记录.md`](验收记录.md)。本轮不测试新 UI、滚轮或 WakeNet。

## 1. 开始前

1. 固件已烧录，保持 30% 播放增益，保留原配对 NVS，无需再次配网或解除配对。
2. 目前用户 Host 的设备接入仍为关闭；ASR/TTS 配置投影为 ready，但运行的是更新前进程。
   请先确保没有进行中的任务，再通过你现有的开发环境管理方式停止旧 Host、启动新候选，
   在 Desktop 设置开启设备接入，等待终端在线。不要用宽泛的 `pkill -f` 停止其他开发任务。
3. 候选 Host 为 `ez-assistant/target/release/ez-assistant-runtime`。该仓还有独立 v0.24 工作区改动，
   本次没有覆盖它们；不要清理工作区或改用旧内置 Host 后声称测的是本候选。
4. 推荐提前启动下方脱敏日志采集。告知我“Host 已重启、设备在线”后，可以一起核对日志再开始。
   真实 Provider 请求会使用你配置的服务，正常产生调用费用；自动化未调用真实 Provider。

## 2. 20 轮实听矩阵

同一会话完成至少 20 个有效逻辑输入；连续分段算一轮，空录音不计入 20 轮。每组结束后空闲
30 秒，保留可比较的资源快照。不要要求 Agent 执行文件、数据库或外部服务写入来测试语音。

| 有效轮次 | 操作 | 重点检查 |
|---|---|---|
| 1～5 | 普通短问短答 | 输入只出现一次，回复完整，返回可操作状态 |
| 6～10 | 每轮连续 2～3 次 PTT 补充输入，在聚合窗口内再次按下 | 上一段继续识别，按顺序合并，只提交一次；按住期间不提前提交 |
| 11～15 | 请求分 3～4 段播报较长内容，每段不超过 `speak` 限制 | 尤其听第二段是否半途停止；不漏段、不乱序、不重播，缓冲稍长可接受 |
| 16～20 | 在前一轮已开始播报时按 PTT，补充新指令 | 旧当前段和余段停止，新输入正常识别；旧音频迟到不能复活 |

额外穿插以下操作，不计入有效轮次：

- 至少 3 次短按/无讲话后释放，再正常输入；不得卡死、丢失下一句或错误重复上一句。
- 至少一次新 PTT 尚未释放时上一轮 TTS 到达；不应播出旧音频干扰本次收音。
- 空闲时关闭再开启设备接入一次；保持配对，自动重新在线，下一轮可正常对话，不重播历史。
- 空闲时正常重启候选 Host 一次、重新插拔设备一次；重新在线后继续输入。按重启分段分析资源，
  不把计数归零当成错误恢复证据，也不把跨重启的 heap 比较当成泄漏证据。
- 真实 Provider 若自然发生失败，记录时间和恢复结果；不要为造故障更换 API Key、删除配置或
  清空用户数据。auth/超时/取消/恢复已有隔离自动化；若实际服务异常需单独复验，先约定安全操作。

## 3. 脱敏日志采集

串口一次只能由一个监控程序占用。以下目录必须不存在；复测时换一个目录名，采集器不覆盖旧证据。
执行前确认 `firmware/build` 已存在；串口默认采 30 分钟，按 Ctrl-C 会保存已有摘要并退出，不复位设备。

```sh
/Users/chenjiale/.espressif/tools/python/v6.0.2/venv/bin/python \
  /Users/chenjiale/github/agent-robot/firmware/tools/media_diagnostics.py \
  --serial /dev/cu.usbmodem101 --duration 1800 \
  --output-dir /Users/chenjiale/github/agent-robot/firmware/build/acceptance-device-01
```

Host 默认后台启动会丢弃 stderr。需要 Host 日志时，先按第 1 节停好旧 Host，再在单独终端以前台方式
启动候选（不要同时启动两份；沿用当前用户 Runtime Home，不新建第二份业务数据）：

```sh
/Users/chenjiale/github/ez-assistant/target/release/ez-assistant-runtime serve \
  --runtime-home /Users/chenjiale/.ez-assistant 2>&1 | \
  python3 /Users/chenjiale/github/agent-robot/firmware/tools/media_diagnostics.py \
  --stdin --output-dir /Users/chenjiale/github/agent-robot/firmware/build/acceptance-host-01
```

采集器仅保留事件白名单、静态原因、时间、数值、脱敏关联 ID；不保存原始串口/Host 行、正文、PCM、
凭据或任意字符串。输出为权限受限的 `events.jsonl` 和 `summary.json`。未知日志被丢弃，采集器
不能替代完整崩溃分析；若看到重启或异常，仍需告知时间，不凭摘要“无错误”宣称验收通过。

定位口径：

- Host `voice_capture_started` 表示已接受 PTT 开始事件；`voice_turn_ready` 是聚合收口；
  `voice_input_accepted` 才是提交 Runtime 成功。分段确认不能当作新的一轮计数。
- `speech_request_*` 是整句 ASR/整段 TTS 的排队和执行耗时，不是 Provider 首包。
- 同一个脱敏 `run` 可关联输入与 `speech_delivery_started`；`request` 可串起合成、预留和下发。
  下行 `stream_id` 可与串口关联，重连后同时参考终端 `connection_epoch` 和时间范围。
- `playback_admission result=accepted` 只表示 Host 接纳；`playback_sent` 只表示发送完成。
  终端 `audio_playback type=1` 表示软件播放完成，`type=2` 是取消，`type=3` 是失败；
  `consumed_samples` 是软件消费进度，不是新增物理 ACK。最终仍需实听。
- FIFO 高水位和 rebuffer 是本次开机累计值；比较每组回到空闲后的 internal heap、最大块、PSRAM，
  不把瞬时缓冲占用、正常取消或单次高水位误判为泄漏/故障。
