# Device Protocol 1.0 密码学与字节编码附录

本文配合[通信协议](通信协议.md)，展开第三方实现必须匹配的密码学字节规则。内容根据当前 Rust、
Node 和 C 实现核对；冻结向量见 [`crypto-v1.json`](../firmware/test/upstream/device-protocol-v1/crypto-v1.json)。
不要用泛化 PAKE 库的默认编码替代本附录，尤其注意应用 transcript 与 SPAKE2 transcript 的长度字节序不同。

## 1. 编码约定

- `UTF8(s)`：字符串原始 UTF-8 bytes，不添加 NUL、不 trim、不改变大小写。
- `U16BE(n)`、`U64BE(n)`、`U64LE(n)`：相应固定宽度整数编码。
- `||`：字节直接拼接。下标切片采用左闭右开区间，例如 `[0:16]` 为前 16 bytes。
- `B64U(bytes)`：URL-safe Base64，无 `=` padding；解码时校验预期长度。
- `I2OSP_BE(n,32)`：整数的固定 32-byte 大端编码，保留前导零。
- 所有 MAC 比较、证书 pin 比较使用常量时间比较；不使用字符串比较验证 MAC。

定义两个不同的编码器，每个 part 都有一个 8-byte 长度前缀，长度不包括前缀本身：

```text
APP(parts) = concat(U64BE(byte_length(part)) || part for part in parts)
RFC(parts) = concat(U64LE(byte_length(part)) || part for part in parts)
```

能力字节 `C` 固定为 7 bytes，每项 false=0x00、true=0x01，按以下顺序排列，**不是位图**：

```text
C = [input_text,
     input_pcm16_16k_mono,
     output_text,
     output_pcm16_16k_mono,
     playback_cancel,
     display_status,
     display_transcript]
```

不能对 JSON 文本直接签名，也不能依赖对象属性顺序、JSON 空白、字符串排序或通用 JSON canonicalization。

## 2. SPAKE2 P-256 参数

终端是 Party A，Host 是 Party B。使用 NIST P-256 / secp256r1，群阶为：

```text
n = ffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551
M = 02886e2f97ace46e55ba9dd7242579f2993b64e16ef3dcab95afd497333d8fa12f
N = 03d8bbd6c639c62937b04d997f38c3770719c629d7014d49a24b4f98baa1292b49
```

`M`、`N` 以上是 SEC1 压缩点编码。wire 中的双方份额以及 transcript 中的共享点必须使用
**SEC1 非压缩编码**：`0x04 || X坐标32bytes || Y坐标32bytes`，合计 65 bytes。
校验对端点在曲线上且非无穷远；去掩码后的点也必须有效，密码学库报错时中止尝试。

### 2.1 从配对码得到密码 scalar

6 位码 `code` 按字符串处理，保留前导零。`request_id` 是本次 pairing request，`installation_id`
是目标 Host 的 TXT 身份值。

```text
P = APP([
  UTF8("ez-assistant-spake2-password-v1"),
  UTF8(code),
  UTF8(request_id),
  UTF8(installation_id)
])
w = OS2IP_BE(SHA512(P)) mod n
```

`w=0` 时中止并建立新尝试。使用加密随机源独立采样 `1 <= x,y < n`，真实尝试不使用 fixtures 的固定 scalar。

```text
终端份额 X = x*G + w*M
Host 份额 Y = y*G + w*N
终端共享点 K = x*(Y - w*N)
Host 共享点 K = y*(X - w*M)
```

`pairing_hello.pake_share=B64U(SEC1_UNCOMPRESSED(X))`；Host 的
`pairing_pake.pake_share=B64U(SEC1_UNCOMPRESSED(Y))`。

### 2.2 应用关联数据 AD

Host 在用户确认配对码后为 `pairing_pake` 新生成 `host_nonce`。这里**不使用**连接初始
`auth_challenge.nonce`。nonce 在 AD 中是 wire 字符串的 UTF-8，不先 Base64 解码。

```text
AD = APP([
  UTF8("ez-assistant-pairing-v1"),
  UTF8(request_id),
  UTF8(installation_id),
  UTF8(certificate_fingerprint),
  UTF8(device_nonce),
  UTF8(pairing_pake.host_nonce),
  C
])
```

`certificate_fingerprint` 是 64 个小写十六进制字符的字符串，**不是**32-byte 解码值。
这将本次 PAKE 与目标 Host、TLS pin、双方 nonce 和声明能力绑定。

### 2.3 SPAKE2 transcript、密钥与双向确认

```text
TT = RFC([
  UTF8(request_id),
  UTF8(installation_id),
  SEC1_UNCOMPRESSED(X),
  SEC1_UNCOMPRESSED(Y),
  SEC1_UNCOMPRESSED(K),
  I2OSP_BE(w,32)
])
schedule = SHA256(TT)
session_key = schedule[0:16]
authentication_key = schedule[16:32]

confirmation_keys = HKDF-SHA256(
  IKM  = authentication_key,
  salt = empty,
  info = UTF8("ConfirmationKeys") || AD,
  L    = 32
)
device_confirmation = HMAC-SHA256(confirmation_keys[0:16], TT)
host_confirmation   = HMAC-SHA256(confirmation_keys[16:32], TT)
```

HKDF 的 empty salt 按标准 HKDF 处理。双方 confirmation MAC 都是完整 32 bytes，没有截断。
终端先验证 `pairing_pake.confirmation_mac=B64U(host_confirmation)`，成功后发送
`pairing_confirm.confirmation_mac=B64U(device_confirmation)`。Host 验证后才接收长期公钥绑定。

注意 `session_key` 是 **16 bytes**，既不是全部 SHA-256 输出，也不是后半段 authentication key。
它仅用于本次临时绑定，不能作为后续长期认证密钥保存。

## 3. Ed25519 长期身份与绑定

PAKE 双向确认后，终端生成新的长期 Ed25519 key pair。私有 seed 为 32 bytes，公钥为原始
32 bytes，签名为原始 64 bytes。使用标准 **Ed25519** 对完整 transcript 签名，不能改用
Ed25519ph、另加预哈希、DER 公钥或 ASN.1 签名封装。

令 `PK` 为原始公钥 bytes：

```text
BT = APP([UTF8("ez-assistant-bind-v1"), AD, PK])
pairing_bind.public_key  = B64U(PK)
pairing_bind.signature   = B64U(Ed25519.Sign(private_key, BT))
pairing_bind.binding_mac = B64U(HMAC-SHA256(session_key, UTF8("device-bind") || BT))
```

Host 验证 binding MAC 与签名，再分配 `device_id`，构造：

```text
CT = APP([UTF8("ez-assistant-commit-v1"), BT, UTF8(device_id)])
pairing_bind_ack.host_proof = B64U(HMAC-SHA256(session_key, UTF8("host-bind-ack") || CT))
```

终端校验 request ID 与 host proof，原子保存 pending 身份后发送：

```text
pairing_commit.signature   = B64U(Ed25519.Sign(private_key, CT))
pairing_commit.binding_mac = B64U(HMAC-SHA256(session_key, UTF8("device-commit") || CT))
```

HMAC 中的标签与 transcript 是**直接拼接**，不能再套 APP，也不添加分隔符。
`pairing_bind_ack` 不是最终持久化成功通知，只有 `pairing_complete` 表示 Host 已完成登记。
成功或失败后销毁 PAKE scalar、临时密钥和敏感中间值，保留经过正确提交的长期身份。

## 4. 每次连接的认证签名

令 `connection_id`、`host_nonce` 来自本次 `auth_challenge`；`device_nonce` 为终端本次新生成随机值；
`C` 为本次 **hello 声明能力**，不是尚未收到的有效能力；`preference` 为精确枚举字符串。

```text
AUTH = APP([
  UTF8("ez-assistant-auth-v1"),
  U16BE(1),
  U16BE(0),
  UTF8(connection_id),
  UTF8(auth_challenge.nonce),
  UTF8(device_id),
  UTF8(device_nonce),
  C,
  UTF8(preference)
])
hello.signature = B64U(Ed25519.Sign(private_key, AUTH))
```

版本值在 AUTH 中是长度为 2 的二进制整数，不是字符 `"1"`、`"0"`。`client_version` 和 envelope 的
`message_id` 不属于 AUTH，但仍必须按协议发送。所有 nonce 和 ID 在 transcript 中均使用字符串
UTF-8 bytes，而非 Base64 解码值。每次连接都签新挑战，不能重放旧 hello。

## 5. 使用冻结向量核验

[`crypto-v1.json`](../firmware/test/upstream/device-protocol-v1/crypto-v1.json) 包含：

1. 配对码、双方身份、nonce、能力、测试专用 scalar。
2. Base64url 编码的 AD、双方份额、双方 confirmation MAC 和 16-byte session key。
3. AUTH transcript、Ed25519 私有 seed、公钥与签名。

按文件中的 `device_scalar_hex`、`host_scalar_hex` 作为测试专用输入重现计算，逐字节比较每个输出。
该文件的 SHA-256 为：

```text

```

绑定阶段还应验证修改 AD、PK、device ID、MAC 标签、能力或偏好时对应签名/证明失败。
fixture seed、公钥、nonce、scalar 和显示码均是公开测试数据，不能复制为产品默认身份或默认配对码。
