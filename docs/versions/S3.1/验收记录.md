### P1 target 首次运行修复记录

- 首次 target 运行在 `device_spake2_party_a_finish()` 返回失败，验证程序按失败策略停止，未将 P1
  标记为通过。
- 根因是 ESP-IDF v6.0.2 的 Mbed TLS 4 已拒绝旧式
  `mbedtls_md_setup(..., hmac=1)`，而 PC host test 使用的 Mbed TLS 3 仍接受该参数。
- 正式 `device_crypto` 组件改为通过公开 SHA-256 流式接口完成标准 HMAC 组合，不改变 SPAKE2
  transcript、key schedule 或 wire bytes，也不引入 target 条件分支。
- 修复后相同 host fixtures 全部回归通过；目标镜像重新烧录并通过写入 hash 校验，实机最终验证通过。

### P2 target 首次运行修复记录

- 首次 target transport 运行完成 Wi-Fi 和 mDNS 后，错误 pin 用例返回
  `CERTIFICATE_UNAVAILABLE`，验证程序停止，未把 P2 标记为通过。
- 根因是 ESP-IDF v6.0.2 的 Mbed TLS 4 默认关闭
  `MBEDTLS_SSL_KEEP_PEER_CERTIFICATE`，握手完成后会释放 peer certificate，无法满足本项目“握手后读取
  原始 DER 再 pin”的安全边界。
- 正式构建配置启用 `CONFIG_MBEDTLS_SSL_KEEP_PEER_CERTIFICATE=y`。该配置约增加 4 KiB TLS heap，换取
  握手后通过公开 API 读取 peer leaf certificate；没有改为 pin 前发送 Upgrade，也没有改用 CA 或跳过
  设备身份校验。
- 修复后实机先以错误 pin 验证阻断，再以正确 pin 完成真实 ez-assistant `/device` Upgrade，并收到、
  严格解码正式 `auth_challenge`；commit `852d4a4` 重新构建和烧录后，启动后约 8.47 秒输出错误 pin
  阻断记录，约 9.53 秒输出
  `target discovery, TLS pin, and WSS validation passed`。

### P2 transport fault 注入记录

- fault Host 每次运行生成临时 RSA 证书，将 leaf DER SHA-256 通过正式 mDNS TXT
  广播；私钥仅存在 `mktemp` 目录，Host 退出时删除，未写入仓库。
- Host 和 ESP32-S3 严格按六个独立 TLS 连接对齐场景：`certificate_rejected`、
  `upgrade_rejected`、`fragment_control_binary_close`、`oversized_text`、
  `partial_frame_timeout` 和 `masked_server_frame`；Host 全部输出
  `transport_fault_scenario_passed`，最终输出 `transport_fault_host_passed`。
- commit `ab5ae2f` 目标镜像通过 flash hash 校验并在 ESP32-S3 rev 0.2 运行；启动后约
  13.42 秒输出 `target transport fault validation passed`，无重启、panic 或未预期连接。
- 验证中修正了 `last_receive_time` 刷新边界：现在只有结构和载荷已完整校验的帧会
  刷新心跳，任意 TLS 字节、半包或非法帧不能持续阻止本地 heartbeat timeout。
