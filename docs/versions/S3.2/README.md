## 阶段目标

以 S3.1 已验收的正式设备链路为基线，先对 agent-robot 终端、ez-assistant Runtime Host、
Device Gateway、SpeechService、Runtime 和 device protocol 做一次实现级整体架构 Review，再完成：

1. ASR/TTS Provider 配置、生命周期、超时、错误分类、降级与恢复收敛。
2. 连续 PTT 输入在 Runtime 提交前的分段聚合、空输入、迟到结果和重传语义收敛。
3. TTS 分段 FIFO、预缓冲、播放确认、取消及迟到音频隔离收敛。
4. 媒体、Provider、队列和 ESP32 内存/任务水位的可诊断基线。
5. 连续至少 20 轮真实 PTT 对话及本阶段故障矩阵验收。

本阶段不是重新实现 S3.1，也不建设另一套 Host 或兼容旧 Demo。架构 Review 的目标是确认当前正式
实现是否具备继续演进的边界；只有取得证据的问题才进入调整。

## 范围边界

### 包含

- 实现级整体架构 Review、决策记录和问题处置清单。
- Host 侧 Provider、输入聚合、TTS 队列、取消和恢复实现。
- 终端侧媒体缓冲、播放边界、资源诊断及必要修正。
- 两仓相关自动化、故障注入和 ESP32 实机验收。
- device protocol 1.0 在不改 wire 前提下的语义核验。

### 不包含

- S3.3 的正式屏幕 UI、滚轮、确认/返回键和菜单。
- S3.4 的 WakeNet 正式链路、物理 AP 完整长稳矩阵和 PCB 输入冻结。
- Opus、双麦、AEC、播放中语音唤醒、OTA、电池或远程 Runtime。
- 旧 Demo Host、旧私有协议或历史消息兼容层。

## 阶段约束

- 架构 Review 完成前只做只读检查、测试盘点和必要的观察性验证，不直接进行结构性重构。
- Review 结论按“保持 / 调整 / 延后”记录；调整项必须有证据、所有者、验证方式和版本归属。
- 若发现必须修改 device protocol，先停止对应实现，提出两仓 schema/fixtures、codec、测试和组合版本
  的完整变更方案，经确认后再解冻；不能单边改 wire。
- ez-assistant 的改动只在 ez-assistant 仓库实施和验证，本仓不复制其正式 Host 代码。
- 生产实现继续遵守正式领域命名，不引入阶段名、临时路径或测试替身控制流。
