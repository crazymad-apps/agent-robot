# S3.1 阶段计划

## 1. 实施原则

- 先通过 codec/密码学/transport 可行性门，再创建完整固件功能。
- S3.1 只有 GPIO21 PTT 一条 ASR 触发通道，不引入 `esp-sr`、AFE 或 WakeNet 任务。
- 每一步只增加一个主要变量；任一安全或 fixture 不一致立即停止后续联调。
- 不复制 S3.0 Demo，不为旧 `ws://`、裸 PCM 或旧控制消息添加兼容代码。
- `firmware/` 是正式产品工程；生产符号不得使用临时、Demo、测试替身或阶段编号命名，命名检查是每个
  阶段门的阻断项。
- 不新增测试专用设备协议。自动化媒体测试复用 ez-assistant fixtures/M7，实机首次媒体验收直接走
  正式 Host 和真实 PTT 链路。
- 不在 agent-robot 中修改 ez-assistant 文件；跨仓改动在对应仓库独立提交和验证。

## 2. P0：冻结可复现输入

### 工作

1. 记录 ez-assistant 实际 commit、dirty diff 摘要、device protocol 版本和 Host 启动配置。
2. 复制/同步 `crypto-v1.json`、`envelope-v1.json`、`pcm-v1.json` 到固件 host tests，并记录来源路径
   与 SHA-256。
3. 固定 ESP-IDF v6.0.2、板卡、分区表和直接依赖版本。
4. 建立 `firmware/` 空工程、组件边界、构建说明和 secret ignore 规则。
5. 建立生产命名检查：release source 中禁止临时性关键字，允许列表仅限第三方 API 固有名称。

### 阶段门

- 两仓版本和 fixtures 可由第三方按记录重新取得。
- 固件空工程可构建，未引入 S3.0 compatibility code。
- project、component、symbol、Kconfig、NVS key 和日志事件均使用正式领域命名。

## 3. P1：codec 与密码学可行性门

### 工作

1. 实现 base64url、长度前缀 transcript、capability 序列化和 strict envelope/PCM codec。
2. 实现 SPAKE2 P-256 party A、confirmation、binding MAC 和认证 transcript。
3. 引入固定版本 Ed25519 实现并记录许可证、来源与 hash。
4. 在 PC host test 与 ESP32 target test 上运行同一组 fixtures。
5. 增加坏 major、额外字段、重复 message ID、坏 PCM header、坏 MAC/signature 和边界长度测试。

### 阶段门

- `crypto-v1.json` 的 share、confirmation、session key、public key、auth transcript 和 signature 逐字节一致。
- envelope 与 PCM fixture 正反例全部通过。
- release 构建不能使用 fixture scalar、固定 seed 或调试配对码。
- 未通过时停止；不得用弱化认证或临时明文绕过。

## 4. P2：发现、TLS pin 与 WSS

### 工作

1. 实现 mDNS 查询和单 Host 选择规则。
2. 实现 TLS 握手后 peer DER SHA-256 pin，确认任何 HTTP/应用字节都发生在 pin 成功之后。
3. 实现最小 RFC 6455 client、64 KiB text 重组、656-byte binary、masking、ping/pong/close。
4. 注入错误指纹、错误 path、坏 Upgrade、fragment、超长 frame、断网和 Host 重启。
5. 实现 Wi-Fi/WSS 串联 Supervisor：Wi-Fi 沿用 1/2/4/8/16/30 秒退避，Device WSS 使用
   1/2/4/8/15 秒 jitter 退避；两层共享 IP/connection epoch 边界，但不共享连接计时器。

### 阶段门

- 正确指纹可进入 WSS，错误指纹抓包确认没有发送 Upgrade 或设备应用消息。
- fragmentation、ping/pong、close 和大小边界与正式 Host 兼容。
- AP、IP、mDNS、Host 端口和 heartbeat 故障恢复符合 [`断线重连设计.md`](断线重连设计.md)，不会
  并发创建多个 socket 或重复累计同一次失败。
- 网络任务故障不阻塞 I2S/LVGL 基础任务。

## 5. P3：配对、认证与持久化

### 工作

1. 在最小 LVGL 状态页显示设备生成的 6 位码；过期后只切换为通用错误状态，不展开正式 UI 设计。
2. 完成 pairing 全序列、pending credential 原子保存、complete 激活和重新认证。
3. 验证掉电点：bind ack 前、保存 pending 后、commit 后但 complete 前。
4. 验证错误码、pairing window 过期、错误确认、Host proof 错误、revoke、连接替换和换 Host。
5. 实现未配对自动扫描：唯一开放 Host 自动连接、多个开放 Host 等待、Desktop 关闭多余窗口后自动继续。
6. 实现上电长按 GPIO21 8 秒并释放的配对重置；完整恢复出厂继续使用串口确认命令。
7. 将配对码固定为启动会话级状态；Host/WSS/window 变化不换显示码，有效短断线续用当前 attempt，
   已失效窗口重建 request/nonce/scalar/share，5 次安全失败才轮换显示码。
8. 在 ez-assistant 将配对码校验、Desktop 输入、Node 生成、Rust/Node crypto fixtures 和 E2E 从 8 位
   原子修改为 6 位；正式 v1.0 尚未发布，不保留 8 位兼容分支。
9. 补齐离线 revoke：Host 验证 revoked identity 的签名后返回 `device_revoked`；终端收到后清长期身份、
   保留 Host pin 并自动进入未配对扫描。

### 阶段门

- 首次配对和重启后的无 token 自动认证均成功。
- complete 丢失可通过 pending 认证恢复，不产生孤儿 identity。
- revoke 后不进入无限普通重连；重置配对后可重新绑定。
- 正常配对不占用 PTT；一个开放 Host 可自动进入，多个开放 Host 不会误绑。
- Host 重启、WSS 关闭/重开和 pairing window 重开后配对码保持不变；有效 attempt 正确续用，失效
  attempt 的密码学临时量已经更新。
- 在线和离线解除配对都能让终端自动进入 `WAIT PAIR`；通用认证失败不会错误清除身份。
- 配对码、private seed 和完整 transcript 不进入普通日志。

## 6. P4：控制状态与媒体

### 工作

1. 实现最小 capability/hello、state、error 和 `audio` output preference；S3.1 不声明或展示
   transcript/text output。
2. 接入 PTT、I2S capture、60 秒 PSRAM cache、正式 PCM header 和 `listen_start/stop/cancel`。
3. 接入 `playback_start/end/cancel`、下行 ring、sample count、75% 默认增益和 underrun 诊断。
4. 验证 listening、stop 后未 accepted、processing、speaking 四种断线语义。
5. speaking 时 PTT：本地立即静音，发送 cancel，再开始新话语。
6. 验证 canonical PCM/ID/preference 重传、120 秒 expiry、旧 epoch 丢弃和 pending input 取消。

### 阶段门

- sequence、方向、尾帧、stream ID、sample count 和 60 秒上限均符合 v1.0。
- 只有 PTT down/up 能开始/结束 ASR 输入；空闲状态不运行 WakeNet 或自动创建话语。
- I2S DMA 不因网络和 UI 阻塞；队列满、ring under/overflow 有明确计数和恢复。
- `input_accepted` 前断线以同一 `client_input_id` 重传，接受后不重复提交。
- speaking 断线不自动重播，播放取消不取消 Runtime Run。
- 20 次 Host 重启循环后无 heap/PSRAM 持续下降，最后一次仍能自动认证并完成 PTT。

## 7. P5：正式首轮端到端

### 工作

1. 使用真实 ez-assistant Host、Device Gateway、SpeechService、当前 Controller Session 和本地
   DashScope 配置。
2. 完成一轮：PTT → PCM → ASR → Runtime → `speak` → TTS PCM → 喇叭，屏幕只投影当前阶段。
3. 重复完成至少 5 轮基本交互，确认不是偶发成功。
4. 记录两仓 commit、固件 hash、协议版本、网络条件、资源快照、各段耗时和已知限制。

### S3.1 完成门

- P0～P4 全部阶段门通过。
- 正式链路至少连续完成 5 轮 PTT，无重复输入、死锁、黑屏、重启或持续音频中断。
- 终端/Host 各重启一次后仍可用保存身份重新认证并完成一轮。
- 验收记录包含真实证据；不能用 S3.0 结果替代。
- S3.2 的媒体/Provider 问题清单和 S3.3 的 Runtime 状态问题清单已经形成。

## 8. 停止条件

出现任一条件立即停止后续实施并记录：

- fixture 与 Rust/Node 正式实现不一致。
- TLS pin 前发送了 HTTP Upgrade 或任何设备应用消息。
- 只能通过跳过证书指纹、明文码、固定密钥或关闭认证才能继续。
- 密码学实现不能逐字节通过共享 fixture。
- 完整语音、配对码、private seed、Runtime Token 或 Provider Key 进入仓库/普通日志。
- 音频或网络处理阻塞 I2S，或内部 heap/任务栈出现持续下降且原因不明。
- 断线重试造成同一 `client_input_id` 的不同 PCM，或造成 Runtime 重复输入。
- 需要协议修改但尚未在 ez-assistant 的 Rust/Node/fixtures/E2E 同步落地。

## 9. 后续阶段边界

- S3.2：ASR/TTS 延迟、分句、队列、Provider 错误、慢设备背压和音质收敛。
- S3.3：current Controller Session、approval、Run/queue 状态、Desktop 同时观察和 Runtime 重启语义。
- S3.4：连续至少 20 轮、完整故障矩阵、组合版本冻结和 PCB 输入参数。
- UI 后续版本：回复正文、transcript、布局、颜色、字体、动效、详细错误和可用性设计；稳定前不启用
  `output_text` / `display_transcript`。
- 自动唤醒后续版本：复用 S2.2/S2.3 的 WakeNet 证据，在正式 WSS/重连/播放取消稳定后单独恢复并验收
  “自动唤醒 + PTT”双入口，本版本不预留运行中的第二通道。
