# S1.0 阶段计划

## 1. 范围

S1.0 只解决“后续可以在什么硬件和工具链上可靠开发”。本阶段不接线验证显示、麦克风或功放，
不实现 LVGL、音频驱动、Wi-Fi、WSS 和 Agent 接入。

## 2. 输入

- [`../../hardware-architecture.md`](../../hardware-architecture.md) 中的首版范围、GPIO 候选和电源约束。
- DevKitC-1 及各分体模块的实物、商品页或数据手册。
- 当前 macOS 开发环境。
- ESP-IDF 官方稳定版本与组件兼容信息。

## 3. 工作分解

### M1：硬件身份与证据

#### 操作

1. 为开发板和每个模块记录正反面清晰照片或商品页。
2. 抄录开发板模组丝印、板卡 revision 和 USB 接口类型。
3. 抄录每个模块的芯片型号、排针名称、逻辑电压和供电电压。
4. 核对喇叭阻抗与额定功率，不依据商品标题推断。
5. 确认面包板、杜邦线、USB 数据线和万用表可用。

#### 产出

- 填写完成的 [`硬件核对表.md`](硬件核对表.md)。
- 每项硬件均具有可回查的照片、链接或数据手册证据。

#### 停止条件

- 模组丝印与商品页不一致。
- 无法确认供电电压或排针定义。
- 开发板不是已确认的官方 DevKitC-1 v1.1 N8R8，或实物信息与照片证据不一致。

遇到停止条件时保留现状，先重新选择或确认硬件，不继续冻结接线。

### M2：工具链安装与冻结

#### 候选决策

- ESP-IDF：v6.0.2。
- 安装方式：Espressif Installation Manager（EIM）。
- target：`esp32s3`。
- 命令行构建、烧录和监视作为可复现基线；IDE 仅作为可选界面。

#### 操作

1. 按官方 macOS 文档安装 EIM 及其前置依赖。
2. 使用 EIM 安装 v6.0.2，不使用浮动 `latest` 作为阶段记录。
3. 打开或激活该版本的 IDF shell。
4. 记录 `idf.py --version`、Python、CMake、Ninja 和交叉编译器版本。
5. 保存 EIM 生成的安装配置位置，但不把机器私有绝对路径写入公共构建逻辑。

#### 验证

```text
idf.py --version
idf.py set-target esp32s3
idf.py build
idf.py flash monitor
```

上述命令是验收动作说明；只有实际退出状态、构建摘要、设备端口和串口启动日志被记录后，
才能判定通过。

#### 停止条件

- EIM 安装或环境激活失败。
- v6.0.2 与实际芯片 revision、USB 驱动或计划组件不兼容。
- 构建依赖了未记录的全局环境或手工路径修改。

### M3：最小工程基线

#### 操作

1. 在当时的 `demo/` 创建最小 ESP-IDF C 学习工程，输出项目名、固件版本和芯片信息，并用板载
   GPIO38 地址灯提供无需外接模块的运行反馈。
2. 设置 target 为 `esp32s3`。
3. 建立 `sdkconfig.defaults`，只保存明确需要的非默认配置。
4. 建立集中式 board config，后续 GPIO 不散落在驱动代码中。
5. 增加构建产物、临时配置和本机环境文件的忽略规则。

#### 预期结构

```text
agent-robot/
├── demo/
│   ├── CMakeLists.txt
│   ├── sdkconfig.defaults
│   ├── idf.sh
│   ├── test.sh
│   └── main/
│       ├── CMakeLists.txt
│       ├── main.c
│       └── board_config.h
└── docs/
```

该结构已在 M2 通过后创建，并在 S1/S2 阶段持续演进；完成 S2.3 后整体归档到
`demos/S2.3/`。此处保留的是当时的计划结构，不代表当前 S3 开发目录。

#### 验证

- clean build 成功。
- 固件可以烧录到实际开发板。
- 串口输出与芯片信息和实物相符。
- 重新打开一个已激活的 IDF shell 后可以复现构建。

### M4：GPIO 与电气复核

#### 操作

1. 使用实际 DevKitC-1 revision 的官方原理图核对所有引出 GPIO。
2. 标记 Boot、USB、Flash/PSRAM、板载 RGB LED 和其他板载占用。
3. 使用各模块实际排针定义核对信号方向和电压。
4. 对 [`../../hardware-architecture.md`](../../hardware-architecture.md) §6 的候选表逐项确认或修订。
5. 记录 3.3V 逻辑支路和 5V 功放支路，不在 S1.0 连接功放负载。

#### 产出

- 一份通过实物和原理图核对的 S1 飞线 GPIO 表。
- 一份电源域与共地说明。
- 对硬件架构基线的必要修订。

#### 停止条件

- 任一 GPIO 与启动、USB 或内部存储占用冲突。
- 模块需要 5V 逻辑输入或输出，不能安全连接 ESP32-S3。
- 开发板 3.3V 支路能力无法从资料或实测中确认。

### M5：S1.0 收口

1. 将实际执行证据写入 [`验收记录.md`](验收记录.md)。
2. 核对所有待冻结项都有明确结论或被移出后续范围。
3. 更新 `docs/versions/README.md` 的阶段状态。
4. 只有验收通过后才开始建立 S1.1 阶段目录和首个单设备验证计划。

## 4. 交付物

- 冻结的开发板和模块身份清单。
- 冻结的 ESP-IDF 版本与可复现激活方式。
- 能在真实开发板运行的最小固件工程。
- 经实物核对的 GPIO 表和电源域说明。
- 完整的 S1.0 验收记录。

## 5. 风险

| 风险 | 处理 |
|---|---|
| 模块商品名与实际芯片不一致 | 以实物丝印、排针和测量为准，不以商品标题冻结 |
| DevKitC-1 revision 导致板载 GPIO 差异 | 到货后读取板卡 revision，并使用对应官方原理图 |
| ESP-IDF v6.0.2 与某个组件不兼容 | 在 S1.0 调研并记录；必要时显式降级，不使用浮动版本 |
| USB 线只能充电 | 使用已验证的数据线，并记录枚举端口 |
| 本机工具版本污染构建 | 使用 EIM 激活环境，记录工具版本和复现步骤 |
| 未拿到全部模块就冻结 GPIO | 未核对项保持待定，禁止进入 S1.1 接线 |

## 6. 阶段完成判定

S1.0 必须同时满足：

- 硬件核对表无影响 S1.1 的未知项。
- ESP-IDF 版本、target 和工具版本已经记录。
- 最小工程在真实 DevKitC-1 v1.1 N8R8 开发板上 build、flash、monitor 成功。
- GPIO 表已用实物与对应官方资料复核。
- 验收记录包含实际命令结果和串口证据。
- 未执行的模块功能没有被描述为通过。
