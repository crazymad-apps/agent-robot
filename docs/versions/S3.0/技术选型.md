# S3.0 技术选型

## 结论

`demo.2` 使用临时 Rust Voice Demo Host、单条设备 WebSocket 和 DashScope 整句 HTTP
ASR/TTS。该实现只验证语音链路，不演化为第二套正式 Host；`demo.3` 继续在同一临时 Host 中引用
ez-assistant `agent-sdk`，验证结束后再联合确定正式 Runtime 接入方式。

| 层次 | 选择 |
|---|---|
| 设备与 Host | 无鉴权 `ws://`，JSON 控制帧 + 裸 PCM 二进制帧 |
| 音频 | PCM16 little-endian、16 kHz、mono、PTT 整句话语 |
| Demo Host | Rust、Tokio、Axum WebSocket、Provider trait |
| ASR | DashScope 北京地域 `qwen-audio-3.0-asr-flash`，Base64 WAV 整句 HTTP 请求 |
| TTS | DashScope 北京地域 `qwen-audio-3.0-tts-flash`、`longanhuan_v3.6`，非流式 HTTP，下载 PCM16/16 kHz/mono |
| 凭据 | 仅 Host 本地 `.env` 中的 `DASHSCOPE_API_KEY` |
| Agent | 相邻仓库 `agent-sdk::Agent::start_ephemeral`，空工具、单 step、独享临时 Recorder |
| LLM | ez-assistant `agent-openai-compatible` + DashScope `qwen-plus` Chat Completions |

## 为什么当前不使用 SSE

设备需要双向控制、上行音频和下行音频，WebSocket 可以在一条连接中覆盖这些需求；SSE 只有
服务器到客户端的事件流，仍需为设备上行另配 HTTP 请求，因此不适合作为设备主通信协议。

DashScope ASR/TTS 的 HTTP 调用是临时 Host 到云 Provider 的内部实现，不是第二套设备通信系统。
当前采用整句请求是因为 PTT 已给出明确话语边界，最少代码即可验证识别与播报。将来如果延迟证据
要求流式化，只替换 Provider 实现，不改变 ESP32 与 Host 的 WebSocket 方向，也不把 SSE 固化到
正式设备协议。

## 边界与后续决策

- 明文、无鉴权 WebSocket 只限受控局域网 Demo，正式版本必须重新设计安全与身份。
- 当前裸 PCM、整句 ASR 和完整 TTS 缓冲优先验证正确性，不代表最终带宽与延迟方案。
- 当前 Host 不承载正式 Session、Run、审批、持久化或恢复，不与 ez-assistant Runtime 分担权威状态。
- `demo.3` 已证明一次性 Agent 执行、连续 20 轮 PTT 及连接/ASR/Agent/TTS 错误恢复；这些证据
  仍不提供正式 Session 语义，下一阶段据此联合决定正式进程拓扑与协议。
