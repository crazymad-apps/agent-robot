# S3.1 方案设计

## 1. 目标与边界

S3.1 的目标不是把 S3.0 Demo 改造成正式固件，而是实现一个最小但完整的正式设备端：

```text
ESP32-S3
  └─ mDNS → TLS pin → WSS /device → pairing/auth → control + PCM
                                                    │
ez-assistant Runtime Host
  └─ Device Gateway → SpeechService → current Controller Session → Runtime
```

本阶段不实现第二套 Host、Desktop SSE 客户端、模型直连、终端会话选择、终端审批、OTA、Opus、AEC
或播放中语音唤醒。S3.0 的 Voice Demo Host 与私有 wire 只保留为历史证据。

## 2. 真值与版本策略

### 2.1 协议真值优先级

发生歧义时按以下顺序处理：

1. ez-assistant `device-protocol-v1` 共享 fixtures。
2. Rust Host 与 Node 模拟终端共同通过的正式实现及 M7 E2E。
3. ez-assistant v0.21 设计附件。
4. 本仓架构和阶段文档。

本仓不手抄一份独立协议成为新的事实源。实施时把 fixtures 作为测试输入同步到固件测试目录，并在
组合版本文件中记录上游提交和 fixture SHA-256；协议实现仍以 ez-assistant 为权威。

### 2.2 联调期协议修改

协议暂时冻结但允许联调修改。只有满足以下条件才修改 wire：

- 当前协议在 ESP-IDF/ESP32-S3 上确实无法安全落地，或 fixtures/两端实现互相矛盾；
- 先形成最小失败用例和变更说明；
- 先在 ez-assistant 同步修改 Rust codec、Node 参考终端、fixtures 和 E2E；
- 根据兼容性递增 protocol minor 或 major；
- 最后同步本仓 C codec 和组合版本记录。

不允许只在 ESP32 侧静默放宽字段、顺序、帧长、认证或错误语义。

## 3. 设备能力

物理终端使用下列 S3.1 最小 capability，不直接套用 Node 的现成 profile：

| capability | 值 | 原因 |
|---|---:|---|
| `input_text` | `false` | 当前终端没有文字输入 UI |
| `input_pcm16_16k_mono` | `true` | S3.1 仅 PTT 语音输入 |
| `output_text` | `false` | S3.1 不显示回复正文 |
| `output_pcm16_16k_mono` | `true` | I2S 功放播放 TTS |
| `playback_cancel` | `true` | speaking 时 PTT 可打断本地播放 |
| `display_status` | `true` | 显示连接、监听、处理、播放和错误 |
| `display_transcript` | `false` | transcript UI 延后设计 |

默认 `output_preference=audio`。能力位必须参与配对和认证 transcript，不能在连接中随意改写；
Host 返回 `hello_ack` 后以 effective capability 为准。PTT 是本地交互事实，不是 protocol v1.0
capability。未来增加回复正文或 transcript 显示时，必须先完成对应 UI 设计，再把 capability 改为
`true`，不能提前声明后静默丢弃 Host 内容。

## 4. 连接与安全设计

### 4.1 发现与 Host 选择

- 使用 `espressif/mdns==1.11.3` 查询 `_ez-assistant._tcp.local.`。
- 读取 SRV/A/AAAA 与 TXT：`protocol_major`、`protocol_minor`、`path`、`installation_id`、
  `certificate_fingerprint`、`pairing_available`。
- 已配对时只自动选择保存的 `installation_id`，并要求发现指纹与保存值一致。
- 未配对且只发现一个开放配对的兼容 Host 时自动进入配对；发现多个开放 Host 时显示
  `MULTIPLE HOSTS`，不随机选择。
- mDNS 消失只触发连接监督和退避，不清除身份。

#### 单按键条件下的自动配对

S3.1 不使用实体按键进入配对模式，也不让 PTT 在 Host 列表中循环选择。自动流程为：

```text
设备已有 Wi-Fi → 开机自动 mDNS 扫描
  → Desktop 只打开目标 Host 的 pairing window
  → 设备发现唯一 pairing_available=true 的兼容 Host
  → 自动连接、生成并显示 6 位码
  → 用户在 Desktop 输入/确认该码
  → 配对完成后设备自动重连并认证 → READY
```

- 未配对时首次立即扫描；未发现开放 Host 时按 2/4/8/10 秒退避并持续扫描。
- 6 位配对码在设备本次上电进入未配对状态时生成一次，只保存在 RAM；Host 重启、WSS 关闭/重开、
  mDNS 暂时消失或 pairing window 到期/重开都保持同一个显示码。
- 多个 Host 可以同时被发现，但只有一个开放 pairing window 时仍可自动选择该 Host。
- 同时有两个以上开放 pairing window 时显示 `ERROR/MULTIPLE HOSTS` 并等待，不允许随机配对；用户在
  Desktop 关闭其他窗口后，下一次扫描自动继续。
- 已配对后只寻找保存的 `installation_id`，忽略其他开放配对的 Host，不会因附近新 Host 自动换绑。
- Wi-Fi 凭据仍沿用 S2.1 的串口录入/NVS；S3.1 的自动扫描不承担 Wi-Fi 配网。

唯一 GPIO21 按键的正常用途保持为 PTT。为解决 identity revoked 或主动换 Host，提供一个不影响普通
使用的配对重置入口：上电前按住 GPIO21，连续保持 8 秒后屏幕显示 `RELEASE TO RESET`，用户释放后
才清除设备 identity/Host pin 并重启；按键卡死或一直不释放不会执行清除。完整恢复出厂仍使用串口
确认命令，避免单键误操作清除 Wi-Fi。

### 4.2 TLS pin 与 WebSocket

`esp_websocket_client` 不能直接满足“自签名证书握手后、发送任何应用数据前读取并固定原始 DER
证书”的实现边界，因此 S3.1 不继续沿用 S3.0 的该组件。设计采用一个隔离的最小 WSS transport：

1. 用 lwIP socket 与 Mbed TLS 建立 TLS 连接；握手阶段不把系统 CA 验证结果当作设备身份。
2. 握手完成立即读取 peer leaf certificate 的原始 DER，计算 SHA-256。
3. 首配对与 mDNS 指纹常量时间比较；已配对与 NVS 中保存的 pin 比较。
4. 不匹配立即关闭 socket，且不发送 HTTP Upgrade、JSON、PCM、设备 ID 或配对消息。
5. 只有 pin 成功后才发送 `/device` WebSocket Upgrade，并验证 HTTP 101、`Upgrade`、`Connection`
   与 `Sec-WebSocket-Accept`。

WebSocket 只实现本协议需要的 RFC 6455 子集：客户端 masking、text/binary、fragment reassembly、
ping/pong、close 和长度校验。控制消息重组上限 64 KiB；PCM binary 必须精确为 656 bytes。transport
内部不解析设备业务消息。

### 4.3 配对与认证

设备链路不使用 Runtime Bearer Token，也不使用预共享 token。安全建立顺序为：

```text
auth_challenge
  → pairing_hello → pairing_pending
  → pairing_pake → pairing_confirm
  → pairing_bind → pairing_bind_ack
  → 本地原子保存 pending credential
  → pairing_commit → pairing_complete
  → 标记 active、断开并重新认证
```

- 设备用安全随机数生成包含前导零的 6 位配对码并只显示在屏幕；配对码不得出现在 wire 或普通日志。
- 配对码的生命周期是当前设备启动会话；每个新的 Host pairing window/协议尝试仍必须生成新的
  pairing request ID、device nonce、SPAKE2 scalar/share 和 message ID，不能因为显示码不变而复用
  已过期的密码学临时量。6 位码把人工输入空间缩小为 `000000`～`999999`，因此 5 分钟窗口、最多
  5 次确认和达到上限立即轮换都属于不可放宽的安全边界。终端还要按当前显示码在 RAM 中累计失败数，
  Host/WSS/window 重启不能把它清零。
- Desktop 用户确认同一配对码后，双方执行 SPAKE2 P-256 和双向 confirmation。
- 设备随后生成 Ed25519 长期身份；Host 只保存 public key。
- `pairing_complete` 丢失时保留 pending credential：下次先尝试认证，成功则激活，失败则清除 pending
  并重新配对。
- 每次认证使用 Host `connection_id`/nonce 与新的 device nonce 签名；新认证连接替换同设备旧连接。
- Host 返回通用 `authentication_failed` 时不无限重试或自动清除身份；可信 `device_revoked` 则按下节
  自动清除长期身份并进入未配对扫描。

同一 pairing window 内的普通 WSS 短断线且 attempt 仍有效时，重发同一 `pairing_hello`，保留 Desktop
正在确认的 pending request。设备已经观察到 window 关闭、attempt 到期或 Host 进程重启后，旧临时量
必须清零；window 重开时使用同一个显示码建立全新的协议 attempt。

配对码只在设备重启、显式重置配对后重启、配对成功，或达到安全失败阈值时失效。Host 的普通生命周期
变化不属于换码条件。达到 Host 当前 5 次失败上限时，设备清零当前 PAKE 上下文并生成新码，避免长期
复用已被反复试错的口令。

#### Host 解除配对

“解除配对”是对已登记设备执行 revoke，不等同于关闭 pairing window：

1. Host 先在 Runtime Store 持久化 revoked 状态。
2. 终端在线时，Gateway 在当前认证 WSS 上发送不可恢复错误 `device_revoked` 并关闭连接。
3. 终端离线时，下次 `hello` 仍由 Host 使用已撤销记录中的 public key 验证签名；签名有效且 lifecycle
   为 revoked 时发送 `device_revoked`。未知 device ID 或签名错误继续统一返回
   `authentication_failed`，不能诱导终端清除身份。
4. 终端只在当前 pinned Host 连接收到可信 `device_revoked` 后，原子删除 device ID、Ed25519 private
   seed/public key 和 pending input，立即静音并清 playback；保留 Wi-Fi，以及该 Host 的
   installation ID/certificate pin 作为重新发现提示。
5. 终端生成新的 6 位启动会话级配对码，自动进入未配对扫描。Host pairing window 未开放时显示
   `WAIT PAIR`；开放后自动产生候选，但仍必须由用户在 Desktop 输入新码，不能静默重新绑定。

ez-assistant 联调树已补齐在线与离线 revoke：Host 对离线 revoked identity 先验签，再返回
`device_revoked`；Node 参考终端清除 credential 后自动回到配对。Rust/Node/Desktop 测试与
M7 离线解除配对端到端用例已通过；实机终端仍须在 P3 复现同一语义。

关闭 pairing window 只清理 Host 当前 pending candidates。未配对终端把 WSS 关闭视为本轮候选结束，
保留 6 位显示码并继续扫描；已经配对的终端和长期 credential 不受影响。

### 4.4 凭据存储

设备身份以一个有版本、长度和状态字段的 NVS blob 保存，内容包括：

- schema version、`pending|active`；
- device ID、Host installation ID、certificate fingerprint；
- Ed25519 private seed 与 public key。

`nvs_set_blob` 与 `nvs_commit` 成功后才发送 `pairing_commit`。日志不得输出 private seed、完整签名、
配对码或完整认证 transcript。S3.1 开发板尚未启用 Flash Encryption/Secure Boot，因此物理提取私钥
是已知原型风险；量产前必须在 PCB/烧录方案中单独关闭该风险，S3.1 不烧写不可逆 eFuse。

提供两个明确操作：

- “重置配对”：只清除设备身份与 Host pin，保留 Wi-Fi；用于 revoke/换 Host 联调。
- “恢复出厂”：清除设备身份、Host pin、Wi-Fi 和用户偏好。

S3.1 的“重置配对”同时提供串口确认命令和上电长按 GPIO21 后释放的单键入口；正常运行时 GPIO21
仍只作为 PTT。“恢复出厂”只提供需要完整确认短语的串口命令，不用单键清除 Wi-Fi。更完整的恢复
交互延后到 UI/交互版本。

## 5. 密码学实现策略

密码学必须先于正式网络联调单独过门：

| 能力 | 实现方向 | 验证要求 |
|---|---|---|
| SHA-256/SHA-512、HMAC、HKDF | ESP-IDF Mbed TLS | host test + target test |
| SPAKE2 P-256 | 隔离封装当前 IDF 的 P-256 点/标量运算 | 完整匹配 `crypto-v1.json` |
| Ed25519 | vendoring Monocypher 4.0.3 optional Ed25519 源码与许可证 | seed→public/signature 逐字节匹配 fixture |
| 随机数 | ESP-IDF 系统熵源/DRBG | 不允许测试标量进入 release 路径 |
| secret 清理 | 显式清零临时 scalar、session key 和 MAC key | 单测与 code review |

ESP-IDF v6.0.2 的 PSA 路径不直接提供当前 SPAKE2 P-256 流程；P-256 封装因此必须独立在
`device_crypto`，禁止业务层调用 Mbed TLS 私有 API。若 IDF 私有 ECP 接口无法稳定构建，立即停在
可行性门，评估固定小型 P-256 实现；不能改成 J-PAKE、明文码或跳过 confirmation。

Monocypher 必须固定 `4.0.3`（该版本包含 Ed25519 timing leak 修复），并记录上游 URL、许可证和
实际 vendored 文件 SHA-256，不使用开发分支。第三方密码学源码不通过 Component Registry 浮动拉取。

## 6. 固件分层

实施工程建议放在根目录 `firmware/`，组件边界如下：

```text
firmware/
├── main/                    # 装配与生命周期
├── components/
│   ├── board/               # 唯一 GPIO/板卡配置
│   ├── device_crypto/       # SPAKE2、Ed25519、transcript、base64url
│   ├── device_identity/     # pending/active NVS blob 与 reset
│   ├── host_discovery/      # mDNS 与 Host 选择
│   ├── wss_transport/       # TLS pin + RFC6455 子集
│   ├── device_protocol/     # strict JSON envelope + PCM codec
│   ├── device_connection/   # pairing/auth/heartbeat/reconnect
│   ├── audio_io/            # I2S capture/playback 与 PCM 转换
│   ├── interaction/         # 单一状态写入者、PTT 与恢复策略
│   ├── ui/                  # 最小 LVGL 状态页，不推断业务状态
│   └── diagnostics/         # 有界指标与脱敏日志
└── test/                    # 上游 fixtures、host tests、故障注入
```

不从 S3.0 复制 connection/controller，不维护旧消息的兼容 codec。允许人工参考并重新实现已经验证的
board GPIO、I2S slot 转换、ST7789 初始化和 75% 默认播放增益。

### 6.1 正式代码与命名

S3.1 是正式产品实现，不存在“先写临时版再改名”的阶段。生产代码遵守：

- ESP-IDF project 使用 `agent_robot_terminal`，固件产物和版本元数据使用产品名，不使用 `s3_1` 或
  `demo`。
- 组件和类型按职责命名，例如 `device_connection`、`pairing_session`、`device_identity`、
  `host_discovery`、`utterance_cache`、`audio_capture`、`audio_playback`、
  `interaction_controller` 和 `ui_presenter`。
- 函数名表达稳定动作，例如 `pairing_session_begin()`、`device_identity_activate()`、
  `utterance_cache_seal()`；不得使用 `do_pair()`、`quick_reconnect()`、`handle_stuff()` 等含糊名称。
- 变量使用协议或领域原名，例如 `pairing_request_id`、`connection_epoch`、`client_input_id`、
  `audio_stream_id`；不得使用 `tmp`、`data2`、`flag1` 或阶段编号代替语义。
- `demo`、`temporary`、`quick`、`hack`、`mock`、`fake`、`test_mode` 和阶段号不得出现在生产符号与
  release 配置中。测试目录可以使用 `mock`/`fake`，但不能被 release 组件依赖。
- 错误码、状态、日志事件和 NVS key 也属于兼容接口，命名后不得随意改动；缩写只使用协议既有术语，
  如 PCM、TLS、WSS、PTT、NVS。

Code review 必须把含糊或临时命名作为阻断项，不以“功能已跑通”为理由保留。

首轮直接依赖固定为：ESP-IDF `v6.0.2`、`espressif/mdns==1.11.3`、
`espressif/cjson==1.7.19~2`、`lvgl/lvgl==9.3.0` 和 vendored Monocypher `4.0.3` optional
Ed25519 文件。S3.1 不依赖 `esp_websocket_client` 或 `esp-sr`；WakeNet 恢复接入时再按阶段二锁文件
复核 `esp-sr` 组合，不能进入 S3.1 的构建依赖或运行任务。

## 7. 任务、队列与内存

### 7.1 FreeRTOS 任务

| 任务 | 主要职责 | 禁止事项 |
|---|---|---|
| Controller | 唯一交互状态写入者、PTT、超时、取消、UI projection | 不做 TLS/JSON/I2S 阻塞调用 |
| Network | discovery、TLS/WSS、codec、心跳、重连 | 不直接操作功放和 LVGL |
| Capture | I2S RX、有效位提取、PCM16、上行帧 | 不等待网络 |
| Playback | 下行 ring → 增益/限幅 → I2S TX | 不等待 UI/网络 |
| UI | LVGL tick、配对码和最小状态渲染 | 不解析正文或推断业务状态 |
| Diagnostics | 周期资源与计数器 | 不记录完整语音/transcript |

S3.1 整个版本不创建 WakeNet/AFE 任务，也不把麦克风保持在常时唤醒监听状态。唯一入口为 GPIO21
PTT：按下开始 `listen_start` 和采集，松开封口并发送 `listen_stop`。自动唤醒在后续独立版本按阶段二
的独立消费者方式重新接入；届时仍保留 PTT，播放期间是否暂停检测也重新验收。

### 7.2 有界缓冲

- Host 上行上限为 60 秒：`60 × 16000 × 2 = 1,920,000 bytes`。设备在 PSRAM 预留一份完整话语
  cache，同时流式发送，不再复制第二份完整 PCM。
- cache 保留到 `input_accepted`；超长时发送 `listen_cancel`、停止采集并显示 `AUDIO TOO LONG`。
- 下行 playback ring 初值 64 帧，即 40,960 bytes / 1.28 秒；以 underrun 和高水位实测调整。
- 控制/event 队列均有固定深度；满队列必须计数并进入显式错误或取消，不能阻塞 I2S DMA。
- WSS control reassembly 使用 PSRAM 的 64 KiB 上限缓冲；常规控制消息仍走小对象路径。

以上是首轮预算，不是验收后的冻结数值。每个阶段门记录 internal heap、largest block、PSRAM、任务栈
水位和音频 ring 高水位。

## 8. 协议与媒体规则

### 8.1 JSON control

- envelope 精确包含 `protocol_major`、`protocol_minor`、`message_id`、`type`、`payload`。
- v1.0 为 major 1 / minor 0；未知字段、空/超长 ID、重复 message ID 和不兼容 major 均明确拒绝。
- message ID 连接内唯一，接收侧保留 256 项 replay window。
- 解析器对每种 payload 做 strict schema 校验，不因 cJSON 能解析就接受额外字段或错误类型。

### 8.2 PCM frame

- PCM16 little-endian、16 kHz、mono、20 ms，payload 固定 640 bytes。
- 每个 WSS binary message 为 16-byte network-order header + 640-byte payload。
- stream ID 非零；sequence 从 0 连续递增，不做缺口恢复。
- PTT 松开时不足 20 ms 的上行尾段补零；v1.0 没有上行原始 sample count，最多引入 20 ms 尾部静音。
- 下行按 `playback_start.sample_count` 只播放有效样本，忽略 Host 尾帧补零。

### 8.3 心跳与重连

- Host 每 15 秒发送应用层 `ping`，设备立即回同 payload 的 `pong`；以 Host 当前 25 秒 timeout 为
  兼容基线，同时正确处理 WebSocket Ping/Pong control frame。
- 重连退避为 1/2/4/8/15 秒并加 jitter；稳定 60 秒后重置。
- TLS pin、认证、协议错误和普通网络断开必须分类，认证/revoke 错误不能被普通重连循环掩盖。
- Wi-Fi 与 Device WSS 使用两个串联 Supervisor：WSS 只在 `GOT_IP` 后运行；每个新连接使用 epoch
  隔离旧回调、队列和 stream。

完整状态机、输入恢复和故障矩阵见 [`断线重连设计.md`](断线重连设计.md)。

## 9. 交互与恢复状态机

```text
boot → wifi → discovering → tls_pin → pairing/auth → idle
                                                   │ PTT down
                                                   ▼
                                                listening
                                                   │ PTT up
                                                   ▼
                                                processing
                                                   │ playback_start
                                                   ▼
                                                speaking → idle
```

规则：

- listening 断线：继续把当前话语写入 PSRAM；重连后以相同 `client_input_id` 和完整 PCM 从 sequence 0
  重传。网络恢复早于 PTT 松开时也先完成本地收音，封口后再从头发送；若达到 60 秒、封口后等待
  120 秒或用户取消则丢弃。
- `listen_stop` 后、`input_accepted` 前断线：同一 ID 完整重传；Host 幂等层处理“已接受但 ack 丢失”。
- `input_accepted` 后 processing 断线：不重复提交；Runtime 继续运行，设备重连后不要求历史回填。
- speaking 断线：立刻静音、丢弃本地下行 ring；重连后不自动重播。
- speaking 时按 PTT：先本地停止播放并发送 `playback_cancel`，然后开始新 `listen_start`；它不取消
  Runtime Run。
- approval：显示 `NEEDS ATTENTION / OPEN DESKTOP`，终端不提供审批操作。
- 任何 error 都必须能通过重连、重置配对或用户再次 PTT 回到明确状态，不无限停在 processing。

设备掉电会丢失尚未 `input_accepted` 的音频 cache，这是 S3.1 可接受边界；不把用户语音持久化到 Flash。

## 10. 最小屏幕与诊断

S3.1 不展开正式 UI 设计。屏幕只显示足以完成配对、确认链路阶段和恢复联调的短状态：

| 状态 | 主显示 |
|---|---|
| boot / connecting | `STARTING` / `CONNECTING` |
| pairing | `PAIRING` 与 6 位码；不在串口输出码 |
| multiple hosts | `ERROR` / `MULTIPLE HOSTS` |
| pairing reset | `RELEASE TO RESET` |
| idle | `READY` |
| listening | `LISTENING` |
| processing | `THINKING` |
| speaking | `SPEAKING` |
| needs_attention | `CHECK DESKTOP` |
| error | `ERROR` 加一个稳定短错误码 |

本阶段不显示 transcript、回复正文、网络详情、波形、录音进度、动画、历史记录或长错误说明，也不做
正式字体、布局、颜色和动效规范。详细屏幕交互在正式链路稳定后的独立版本展开，届时再启用
`output_text` / `display_transcript` capability。

普通日志只记录阶段、耗时、字节/帧数、sequence、水位、RSSI、重连次数和脱敏 ID 后缀。完整 PCM、
transcript、reply、配对码、私钥、Runtime Token 与 Provider credential 均不记录。

## 11. 选型结论与保留风险

| 项 | 结论 | 保留风险/处理 |
|---|---|---|
| 终端 transport | mDNS + 自建最小 pinned-TLS WSS | 先以真实 Host 证书做实机 spike |
| JSON | cJSON 严格 schema wrapper | 64 KiB 极值需 PSRAM/故障测试 |
| UI | ESP LCD + LVGL 最小状态页 | 正文、布局与动效延后独立设计 |
| Ed25519 | 固定 Monocypher optional source | 记录许可证、tag、hash、fixture |
| SPAKE2 P-256 | 隔离 Mbed TLS ECP 实现 | IDF 私有 API 漂移；固定 6.0.2 并设构建门 |
| 话语恢复 | PSRAM 单份 60 秒 cache | 约 1.92 MB；需验证最大连续块 |
| 安全启动 | S3.1 不烧 eFuse | 原型私钥物理提取风险，量产前关闭 |
| 协议版本 | 暂时冻结 1.0 | 改动必须先更新 ez fixtures/E2E |
